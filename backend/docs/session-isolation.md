# Session isolation

Each successful login creates a separate database session with a unique token hash and session-bound CSRF token. No global logged-in-user flag exists. Different browser cookie jars may authenticate different users, including multiple users of the same role, simultaneously. Logout revokes only its authenticated session; password changes revoke all sessions belonging to that account.

`auth.integration.test.ts` verifies simultaneous sessions for an admin, caregiver and two different seekers, then logs out the caregiver and verifies that the other accounts remain authenticated. The 32-test PostgreSQL integration suite passed on 22 November 2026.

The browser now supports different accounts in separate tabs, including two seekers. Each tab keeps a random non-secret account context in sessionStorage. API calls send X-Account-Context; the Next gateway selects only its context-named HttpOnly cookie and scopes response cookies to that context. Bearer tokens never enter browser storage or JavaScript. Invalid contexts return 400 and unknown contexts cannot fall back to another cookie. Legacy API clients retain their original cookie contract.

Sign-in/signup remain accessible while other accounts are active. A successful login selects a fresh context only in that tab; failed logins preserve the previous selection. Reload and navigation retain it. Remember-me saves only a default context identifier in localStorage; already-open tabs remain independent. Duplicating a tab may initially copy its selection, as browsers copy sessionStorage; a new login separates it. Logout broadcasts and cookie expiry are scoped to the selected context. Password changes still revoke all server sessions for that account.

Document navigation cannot carry the tab's API header. When context cookies exist, the proxy serves only the dashboard shell; AuthBoundary validates the tab's identity before rendering content. Every protected data API still checks authentication, role, ownership, profile completion and CSRF. A forged context cookie cannot authorize data. Wrong-role dashboard visits return to that tab's authorized dashboard. This is shared-browser convenience, not a security boundary against someone controlling the browser profile; use separate profiles for mutually untrusted users.

Verification: `npm run test:flow` covers 101 backend tests, 14 UI/loading/context tests and 32 database integration tests. After `npm run build`, `node .tools/verify-http.cjs` runs 6 HTTP tests, including multiple accounts in a shared cookie jar, invalid/unknown contexts, role/CSRF isolation and independent logout. Browser click-through verification is not claimed by these automated suites.

Manual check: sign into seeker A in tab 1; open `/signin` in tab 2 and sign into a caregiver; open `/signin` in tab 3 and sign into seeker B. Refresh and navigate each tab, then log out tab 2. Tabs 1 and 3 must retain their accounts. Repeat with admin and remember-me.

Public website navigation: the header now checks the tab's session, shows its account name/role, and links to its own dashboard (or required profile-completion page). Focus, pageshow and browser history navigation recheck the session without forcing public visitors to sign in. Caregiver and care-request cards open details dialogs instead of hard-coded sign-in links. Public profile fields remain filtered by the backend; care-request details use the existing authenticated, owner/role-scoped endpoint. The dialog offers a role-appropriate dashboard continuation, with sign-in reserved for guests. Organisation enquiry links also respect the active tab's account. The UI suite now has 19 passing tests, including rendered public-header and listing behavior. Browser automation was unavailable for the recovery session; back-button and mobile click-through checks remain manual.

Backend startup recovery: duplicate instances caused EADDRINUSE on port 4000. A clean restart exposed PostgreSQL 53300 because pgAdmin held all 100 client connections. Stopping that pgAdmin background process released them; the backend started and `/api/v1/health/ready` returned ok. No database records were reset or removed. The app now labels connections my-carer-api, defaults to a maximum of 5 per process (DATABASE_POOL_MAX), and releases idle pooled connections after 10 seconds. This bounds the app's pool but cannot prevent another application exhausting PostgreSQL. Keep one local backend on port 4000; duplicate startup now includes an actionable message.

These functional tests do not establish capacity for millions of users. Traffic/load testing, deployment sizing and ingress rate-limit configuration remain separate work.
